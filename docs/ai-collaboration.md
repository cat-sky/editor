# AI 协助及编写规范

> 本文档定义 AI 助手与人类开发者的协作规则、三阶段开发流程及文档编写标准。
> 所有协作必须遵循此规范，确保开发过程可控、可追溯、可维护。

---

## 一、协作原则

### 1.1 核心哲学

- **人类主导**：AI 是协作者，不是决策者。架构方向、产品逻辑、用户体验由人类最终拍板。
- **文档先行**：任何实现之前，必须先完成对应的设计文档和接口定义。
- **透明操作**：AI 的所有修改必须可追溯、可解释、可回滚。
- **渐进信任**：随着协作深入，可逐步放宽 AI 的自主权限，但需明确记录。

### 1.2 默认假设

- AI 不了解业务背景，除非人类主动提供。
- AI 不了解代码历史，除非人类提供上下文或 AI 主动查阅 Git 记录。
- AI 的"最佳实践"建议需经人类确认是否适用于本项目。

## 二、三阶段开发流程

本项目采用严格的**三阶段开发模式**，禁止跨阶段操作。

### 第一阶段：基础规范建立

**目标**：建立项目基础文档，作为后续开发的契约。

**交付物**：
1. **项目依赖说明**（`docs/dependencies.md`）
   - 记录所有技术依赖及其用途
   - 明确项目搭建方式（`electron-vite`）
   - 定义依赖管理规则

2. **项目架构及目录结构**（`docs/architecture.md`）
   - 定义整体架构模式（Electron + React + TypeScript + Vite）
   - 明确 `electron-vite` 标准目录结构
   - 规定三层职责边界（Core / Services / Workbench）
   - 定义新模块判断规则
   - 规定目录命名约定
   - 明确文档分类存放规则

3. **AI 协助及编写规范**（本文档）
   - 定义协作原则与权限分级
   - 明确三阶段开发流程
   - 规定文档编写标准
   - 制定代码交付规范

**执行规则**：
- 此阶段由人类主导，AI 辅助起草
- 所有文档需经人类确认后方可定稿
- 文档定稿后进入第二阶段

---

### 第二阶段：模块设计与接口定义

**目标**：设计具体功能模块，编写使用文档及接口文件，**不编写具体实现**。

**文档存放规则**：
- Core 层模块文档 → `docs/core/<模块名>.md`
- Services 层模块文档 → `docs/services/<模块名>.md`
- Workbench 层模块文档 → `docs/workbench/<模块名>.md`
- 开发指南 → `docs/guides/<指南名>.md`

**交付物**（每个模块）：
1. **模块设计文档**（按类型放入对应 docs 子目录）
   - 模块职责边界（负责什么、不负责什么）
   - 使用场景与示例
   - 依赖关系（依赖哪些模块、被哪些模块依赖）
   - 状态与数据流设计
   - 异常处理策略

2. **接口定义文件**（TypeScript 类型文件）
   - Props 接口定义
   - 函数签名定义
   - IPC 通信接口定义（如涉及主进程）
   - 状态类型定义

3. **模块 README**（模块代码目录内 `README.md`）
   - 快速开始示例
   - API 索引
   - 注意事项

**执行规则**：
- **禁止编写任何具体实现代码**（函数体、组件 JSX、Hook 逻辑等）
- 仅定义类型、接口、函数签名
- 所有接口需经人类 Review 确认
- 接口确认后锁定，进入第三阶段方可实现

**示例（允许的内容）**：

```typescript
// ✅ 允许：接口定义
export interface FileNode {
  id: string;
  name: string;
  type: 'file' | 'directory';
  children?: FileNode[];
  isExpanded?: boolean;
}

export interface FileExplorerProps {
  rootPath: string;
  onFileSelect: (file: FileNode) => void;
  onFileOpen: (file: FileNode) => void;
}

// ✅ 允许：函数签名（无实现）
export function useFileSystem(rootPath: string): FileSystemState;
export function buildFileTree(path: string): Promise<FileNode[]>;

// ❌ 禁止：具体实现
export function useFileSystem(rootPath: string) {
  const [files, setFiles] = useState([]);  // ← 禁止！
  // ... 具体逻辑
}
```

### 第三阶段：具体代码实现

**目标**：根据第二阶段的文档和接口文件，编写具体实现代码。

**执行规则**：
- 严格遵循第二阶段定义的接口，不得擅自修改
- 如需修改接口，必须回退到第二阶段重新设计
- 实现过程中发现接口问题，记录并反馈，不擅自绕过
- 每个模块实现完成后，同步更新模块 README 中的使用示例

**AI 权限分级**：

| 级别 | 名称 | AI 权限 | 人类参与 | 典型场景 |
|------|------|---------|----------|----------|
| **L1** | 自动执行 | 直接修改文件 | 事后 Review | 代码格式化、Lint 修复、补充 JSDoc、简单重构 |
| **L2** | 建议模式 | 提供方案，人类确认后执行 | 先审后做 | 新增依赖、调整实现方式、优化算法 |
| **L3** | 讨论模式 | 分析利弊，提供多个选项 | 共同决策 | 修改已锁定接口、调整架构、安全相关变更 |

**禁止擅自操作（黑名单）**：

- ❌ **绝不执行**：`npm install` / `npm uninstall` / 修改 `package.json` 依赖（L2 需确认）
- ❌ **绝不执行**：`git reset --hard` / 强制推送 / 删除未跟踪文件
- ❌ **绝不执行**：修改 `.env`、密钥文件、CI/CD 配置
- ❌ **绝不执行**：修改第二阶段已锁定的接口定义（必须回退到第二阶段）
- ❌ **绝不生成**：无意义的占位代码（如空 `// TODO` 函数、假实现）
- ❌ **绝不假设**：人类未明确说明的需求，AI 不得自行脑补实现

## 三、文档编写标准

### 3.1 通用格式

- **格式**：Markdown（`.md`）
- **编码**：UTF-8
- **换行**：LF
- **行宽**：建议每行不超过 100 字符
- **标题层级**：最多 4 级（`#` 到 `####`）

### 3.2 必备元信息

每篇文档开头必须包含：

```markdown
# 文档标题

> 一句话描述本文档目的

- 创建日期：YYYY-MM-DD
- 最后更新：YYYY-MM-DD
- 作者：姓名 / AI 辅助
- 状态：草稿 / 评审中 / 已发布 / 已归档
```

### 3.3 内容质量标准

- **一个文档一个主题**：不要试图在一篇文档里解决所有问题
- **先给结论再给细节**：读者应能在 30 秒内了解核心信息
- **代码示例可运行**：所有代码块必须是语法正确、可复制的
- **链接可追踪**：引用外部资源需附链接，引用内部文档需附相对路径

### 3.4 禁止事项

- ❌ 空洞的标题（如"概述"、"介绍"）
- ❌ 过时的截图（优先用文字描述 + 代码）
- ❌ 无上下文的代码块（必须说明这段代码解决什么问题）
- ❌ 口语化表达（"我觉得"、"可能吧"，改为确定性陈述）

## 四、代码交付规范

### 4.1 AI 生成代码的标记

复杂逻辑或临时方案需标注：

```typescript
// AI-generated: 基于假设 X 生成，需人类 Review
function complexLogic() { ... }

// AI-generated: 临时方案，建议后续替换为官方 API
const workaround = () => { ... }
```

### 4.2 变更原子性

- 每次变更聚焦单一职责
- 提交信息（commit message）需说明 AI 参与程度：
  - `feat: 添加文件树组件`（AI 辅助）
  - `refactor: 提取 IPC 通道常量`（AI 生成，人类 Review）

### 4.3 测试与验证

- AI 生成的新功能代码，需同步提供测试思路或测试用例
- AI 修改现有代码后，需说明可能影响的测试范围

## 五、沟通协议

### 5.1 任务启动清单

每次新任务开始时，AI 必须确认以下信息：

```markdown
【任务确认】
- 当前阶段：第一 / 第二 / 第三阶段
- 当前分支：main / feature/xxx
- 任务目标：xxx
- 涉及文件：src/xxx, src/yyy
- 变更范围：L1 / L2 / L3
- 已知约束：TypeScript 严格模式 / Electron 安全要求 / ...
```

### 5.2 假设声明

AI 做技术决策时，必须显式声明假设：

> **假设**：本项目使用 Zustand 做状态管理，因为依赖少、TypeScript 支持好。
> 如不符合预期，请告知替代方案。

### 5.3 风险预警

以下情况 AI 必须主动提示风险：

- 性能影响（如大列表渲染、频繁 IPC 通信）
- 安全隐患（如 `nodeIntegration: true`、XSS 风险）
- 兼容性破坏（如 Electron 版本升级、API 变更）
- 可维护性下降（如过度抽象、魔法字符串）

### 5.4 拒绝机制

人类有权随时说"停"，AI 必须：

1. 立即停止当前操作
2. 说明已完成的步骤
3. 提供回滚方案（如有）
4. 等待新的指令

## 六、阶段切换规则

| 切换方向 | 条件 | 操作 |
|----------|------|------|
| 第一阶段 → 第二阶段 | 所有基础文档已确认定稿 | 创建模块文档目录，开始模块设计 |
| 第二阶段 → 第三阶段 | 模块接口已确认锁定 | 在模块代码目录内创建实现文件 |
| 第三阶段 → 第二阶段 | 发现接口设计问题需修改 | 标记接口为"修订中"，暂停实现 |
| 任何阶段 → 第一阶段 | 基础规范需调整 | 更新对应基础文档，重新确认 |

---

## 七、争议解决

1. **技术分歧**：以项目长期可维护性为最高优先级，必要时引入第三方资料佐证
2. **权限争议**：默认降级处理（L1 → L2，L2 → L3），人类拥有最终解释权
3. **文档冲突**：以最新版本为准，Git 历史作为追溯依据
4. **阶段争议**：如需跨阶段操作，必须经人类明确授权
